# CLAUDE.md

Genesys-Cloud-App ("Polly"): Umfragen im Vue-Frontend pflegen, als Data-Table-Zeilen in Genesys ablegen, vom Architect Call Flow abspielen lassen; Antworten landen über ein Amplify-Gen-2-Backend in DynamoDB.

## Befehle

- `npm run dev` – Vite-Dev-Server. `/api` wird auf eine **fest verdrahtete** API-Gateway-URL in `vite.config.ts` proxied (nicht aus `amplify_outputs.json`); bei eigenem Backend dort anpassen.
- `npm run build` – nur Frontend (`dist/`, gitignored), zwei Einstiegspunkte: `index.html` (Genesys-App) und `survey.html` (öffentliche Umfrageseite). Kein Typecheck im Build.
- `npm test` – führt `test/surveyFlowTranslator.test.ts`, `surveyResponsesExport.test.ts`, `surveyDeletion.test.ts`, `genesysRegion.test.ts`, `flowPayloadBudget.test.ts`, `ttsTextLimit.test.ts`, `technicalName.test.ts`, `surveyValidation.test.ts`, `surveyRow.test.ts`, `invitationToken.test.ts`, `flowNavigation.test.ts`, `webSurveyBackend.test.ts`, `invitationLinks.test.ts`, `webSurveyPage.test.ts`, `webTheme.test.ts`, `featureFlags.test.ts`, `surveyExistence.test.ts`, `customerApi.test.ts`, `ttlCache.test.ts`, `surveyRules.test.ts`, `domainImports.test.ts`, `mcpSurveyPipeline.test.ts`, `mcpPseudonym.test.ts` und `mcpInfrastructure.test.ts` nacheinander per `tsx` aus (eigene Mini-Test-Funktion, kein Vitest/Jest). Weitere Testdateien müssen explizit ins `test`-Script aufgenommen werden.
  - Einzeltest: keinen Filter vorhanden – Datei direkt ausführen: `npx tsx test/<datei>.ts`.
  - Im Claude-Sandbox scheitert `tsx` mit `listen EPERM …tsx-*.pipe`; dann `node --import tsx test/surveyFlowTranslator.test.ts` verwenden.
- Typecheck (kein Script, kein Linter/Formatter im Projekt): `npx vue-tsc --noEmit`. Muss fehlerfrei durchlaufen (prüft auch `amplify/`). Fehlerhafte Typen in `node_modules` (z. B. PrimeVue-Eventbus) werden per `skipLibCheck` ignoriert.
- `python3 tools/api_tests.py` – Testsuite gegen die **deployte** API (nur Standardbibliothek), eine Zeile pro Test, bei Fehler Abweichung von der erwarteten Antwort; Exit-Code 1 bei Fehlern. Token und URL nur aus der Umgebung: `GENESYS_TOKEN` (Bearer aus dem Genesys-Portal), `API_URL` (Pflicht, ohne bricht das Skript ab), optional `GENESYS_REGION`, `GENESYS_TOKEN_NO_DEPLOY` (403-Fall Web-Designs). Optional `API_CLIENT_ID`, `API_CLIENT_SECRET`, `API_TOKEN_URL` für die Kunden-API-Fälle (`tests_customer_api`, sonst übersprungen). Umfrage-IDs u. a. per Parameter (`--survey-id`, `--survey-name`, `--survey-version`, `--datatable-id`, `--existing-survey-id`, `--preview-survey-id`, `--web-token`, `--web-theme-write`, siehe `--help`). Die öffentlichen `/web-survey`-Fälle laufen vorab auch ohne Token. Einladungen für die Web-Fälle erzeugt das Skript selbst über `POST /invitations` (gültig 1 h bzw. 5 s für den Ablauf-Fall; `--web-token` überschreibt die gültige), das braucht `polly_deploy` und einen Prod-Stand von `--survey-id`. Schreibt echte Daten. Neue Fälle: `suite.case(...)` in einer `tests_*`-Funktion; Requests über `api.genesys(...)` (mit Token) bzw. `api.public(...)`.
- `tools/run_api_tests.sh` – Wrapper für `api_tests.py`: lädt die Variablen aus `tools/run_api_tests.env` (gitignored, Vorlage `tools/run_api_tests.env.sample`; enthält Token und Client-Secret) und reicht Optionen durch. Der Entwickler trägt die Werte lokal ein; nie Token oder Secrets ausgeben, zitieren oder in die Datei schreiben. Ausführen nur, wenn `GENESYS_TOKEN`, `SURVEY_ID` und `API_URL` gefüllt sind und `API_URL` zum aktuellen Branch passt. Sinnvoll meist erst, wenn die Änderung nach Amplify gepusht und deployt wurde. Schlägt `[G1]` (`/users/me`) fehl, ist das Token abgelaufen: abbrechen und den Entwickler um ein neues bitten. In der Claude-Sandbox brechen Antworten über ca. 8 KB zufällig ab (`IncompleteRead`/`RemoteDisconnected`, kein API-Fehler): den Test dann vom Entwickler im Terminal ausführen lassen. Schreibt echte Daten.
- Backend-Deploy nur über Amplify-Pipeline (`amplify.yml` → `npx ampx pipeline-deploy`). Lokal ggf. `npx ampx sandbox` (erzeugt `amplify_outputs.json`, `.amplify/`).

## Architektur

- **Frontend** (`src/`, Vue 3 + Pinia + PrimeVue 4 + Tailwind 4): Läuft als Genesys-App-Integration, Login per Implicit Grant (`services/genesys_helper.ts`), alle Genesys-Calls über `purecloud-platform-client-v2`-Instanzen im `appStore`.
- **Speicher der Umfragen ist eine Genesys Data Table**, keine eigene DB. Das Setup legt `<projectTag>_polly_surveys` (Umfragen + `__meta`/`__lock`) und `<projectTag>_polly_mapping` an und merkt sich beide in `meta.setup.dataTable` / `mappingDataTable`; die App bekommt die IDs als `datatable_id` / `mapping_datatable_id` in der Start-URL. Keine festen Tabellennamen im Code. Zeilen: `survey_<uuid>` (Felder Draft/Stage/Prod/Backup), `survey_list` (Index im Feld Draft), dazu `__meta` / `__lock`.
- **Queue-Mapping** liegt in einer zweiten, eigenen Genesys Data Table mit Spalten `QueueName` (Key), `SurveyId`, `DeliveryRate` – eine Zeile pro Queue, siehe `documentation/datatablerow_queue_mapping.md`; Zugriff über `services/queueMappingService.ts`.
- **Draft vs. Flow-Format**: Draft = baumförmiges Editor-JSON (`domain/survey/surveyTypes.ts`, Regeln in `surveyRules.ts`, Meldungen über den Adapter `surveyValidator.ts`). Stage/Prod = flaches, verkettetes JSON für Architect, erzeugt von `domain/survey/flowTranslator.ts` (Frontend über den Adapter `services/surveyFlowTranslator.ts`). Deploy nach Prod kopiert vorher Prod → Backup (Rollback).
- **Editor-Logik** liegt in `composables/useSurvey*.ts`, Data-Table-I/O in `services/surveyService.ts` (Zeilen `survey_<id>` werden nur über `updateSurveyRow` geschrieben: frisch lesen, Patch anwenden) und `services/genesys/*`; reine Regeln ohne Vue/Store in `domain/survey/*` (Prüfregeln `surveyRules.ts`, Translator `flowTranslator.ts`, Payload-Messung `flowPayload.ts`, Zeilenaufbau und `survey_list` `surveyRow.ts`, Lock-Regeln `surveyLock.ts` – beide von App und `survey_store.ts` gemeinsam genutzt, keine Kopien im Backend, Feld-IDs `surveyFieldIds.ts`); Komponenten in `components/survey/` sind nur Darstellung.
- **Backend** (`amplify/backend.ts`, CDK direkt): eine HttpApi, Lambdas `onboarding`, `survey_responses` (Flow schickt Antworten schrittweise; nimmt nur Umfragen an, deren Zeile in der Data Table des Mandanten existiert, über `checkSurveyExists` mit Cache 30 min / 5 min / 60 s; bei unklarem Ergebnis wird trotzdem gespeichert, Konfigurationsfehler werden als `SURVEY_CHECK_CONFIG_ERROR` geloggt), `survey_responses_export` (CSV-Export in Teilabrufen, nur lesend), `survey_responses_delete` (löscht Ergebnisse gelöschter Umfragen asynchron über SQS, prüft selbst gegen die Data Table), `survey_cleanup` (EventBridge, markiert Sessions als `timed_out`), `invitations` (signiert Einladungs-JWTs, nur Genesys-User mit `polly_deploy`, serverseitig geprüft), `web_themes` (Web-Designs pro Mandant in `WebSurveyThemesTable`; lesen jeder App-Nutzer, schreiben nur `polly_deploy`, serverseitig geprüft) und `web_survey` (öffentlich, ohne `resolveTenantContext`; liest Prod über die Client Credentials des Mandanten, liefert das Design mit, speichert per Transaktion). Gemeinsame Bausteine in `amplify/functions/shared/` (u. a. `survey_results.ts` für Aggregate/Lösch-Tombstone, `genesys_survey_check.ts` mit `loadProdSurvey` und `checkSurveyExists`, `installation_meta.ts` (Projekt-Tag, Flags und Standard-Basis-URL aus `__meta` in einem Zugriff, 60 s gemerkt), `invitation_keys.ts` für den Schlüssel aus Secrets Manager, `caller_roles.ts` für die serverseitige Rollenprüfung, `web_themes.ts` mit `pickTheme`, `http.ts` mit `fetchWithTimeout` (Genesys-Timeout, auf die Lambda-Timeouts abgestimmt) und `readRequestBody`, `ttl_cache.ts` mit `TtlCache` für alle Caches im Lambda-Speicher, Laden über `getOrLoad` (`ttlMs: 0` = Ergebnis nicht merken) – keine eigenen Caches mehr bauen). Mandantenauflösung in `amplify/functions/shared/tenant_auth.ts` (Cognito-M2M-Token **oder** Genesys-Bearer + `x-genesys-region`).
- **Berechtigungen** (Frontend, Bedienschutz; serverseitig geprüft wird nur `polly_deploy` bei `POST /invitations` und beim Schreiben von `/web-themes`, gleiche Namenslogik über `domain/permissions/roleCheck.ts`): Genesys-Rollen `polly_write` (Umfragen anlegen/bearbeiten/löschen) und `polly_deploy` (Deploy/Rollback/Queue-Mapping), `polly_reporting` (Ergebnis-Export). Sie werden beim Login geladen, die Getter `canWrite`/`canDeploy`/`canExport` im `appStore` liefern die Rechte, siehe `documentation/permissions.md`.
- **Web-Kanal** (in Arbeit, Plan mit Fortschritt: `documentation/implementationsplan_web_surveys.md`, Spezifikation: `documentation/polly_web.md`): öffentliche Umfragen über JWT-Einladungslinks, gerendert aus dem Prod-Flow-JSON. Der Draft hat dafür `base_url` (leer: Standard-Basis-URL des Mandanten aus `__meta.web.defaultBaseUrl`, Einstellungen, Karte `components/webSettings/WebDefaultBaseUrlCard.vue`, Schreiben über `services/metaSettingsService.ts`; Lambdas lesen sie mit `loadDefaultBaseUrl` in `installation_meta.ts`, Auswahl über `pickBaseUrl`), `language` und bei rating/nps `options.min_label`/`max_label` (alle optional; `base_url` kommt nicht ins Flow-JSON). Backend steht (Lambdas `invitations`, `web_survey`, Tabelle `InvitationTokens`, Secret `polly-web-survey-jwt-<envSuffix>`, Drosselung pro Route in `backend.ts`). Einladungs-Unterseite steht (`/surveys?id=…&invite=1`, `SurveyInvitationView.vue`, Link-Aufbau und CSV rein in `domain/survey/invitationLinks.ts`; CSV-Escape/Formelschutz gemeinsam mit dem Report-Export in `utils/csv.ts`). Die öffentliche Umfrageseite ist ein zweiter Vite-Einstiegspunkt (`survey.html`, `src/webSurvey/`, erreichbar unter `/s/<jwt>` per Amplify-Rewrite bzw. Plugin in `vite.config.ts`): ohne Genesys-SDK, Pinia, Router, PrimeVue, `appStore` und ohne die App-Locales – eigene Texte in `src/webSurvey/i18n/` (`de`/`en`/`fr`), reine Logik in `domain/survey/webSurveyPage.ts`, Navigation über `flowNavigation` direkt auf dem bereinigten `WebSurvey`. Öffentlich erreichbar: keine Ausgabe als HTML (`v-html`), keine fremden Quellen (CSP wird beim Build in `survey.html` eingefügt), keine Abhängigkeiten der App in `src/webSurvey/` importieren. **Web-Designs** (Plan: `documentation/implementationsplan_web_designs.md`): nur Tokens (`domain/webTheme/webTheme.ts`, aliasfrei, gemeinsam mit Lambdas), auf der Seite als `--ws-*`-Variablen per `applyTheme.ts`; Schriftgrößen in `webSurvey.css` nur in den Rollenklassen, keine Tailwind-Textklassen in `src/webSurvey/`. Pflege in den Einstellungen (`components/webTheme/`, Live-Vorschau über `survey.html?preview=1` per `postMessage`), Auswahl pro Umfrage über `web_theme_id`. Schreiben geht auch per Kunden-API-Scope `themes.write` (Import, Upsert nach `themeId`, ohne optimistisches Sperren), gemeinsame Schreiblogik `saveWebThemes` in `shared/web_themes_table.ts` (jedes Speichern erhöht unter Bedingung den Verwaltungseintrag `#revision` des Mandanten in derselben Tabelle; Lesen nur über `queryWebThemeItems`, das ihn ausblendet). **Webvorschau** (Button in der Deployment-Ansicht, `useWebPreview.ts`): `POST /invitations/preview` signiert einen Token mit Claim `stage: true` (7 Tage, `PREVIEW_TOKEN_TTL_SECONDS`, in `verifyInvitation` erzwungen); `web_survey` liest dann die Spalte `Stage` (`loadFlowSurvey`), meldet `preview: true` und speichert beim Absenden nichts.
- **Kunden-API** (in Arbeit, Plan mit Fortschritt: `documentation/implementationsplan_external_api.md`, Kundenspezifikation: `documentation/polly_customer_api.md`, Betrieb: `documentation/betrieb_api_zugaenge.md`): versionierte Routen `/ext/v1/…` an der App-HttpApi, Anmeldung per Cognito Client Credentials mit fachlichen Scopes (`polly-api/reporting.read`, `invitations.write`, `surveys.read`, Konstanten in `amplify/functions/shared/api_scopes.ts`, auch von `backend.ts` importiert). Der Mandant kommt nicht aus dem Scope, sondern über die `client_id` aus `ApiClientsTable` (GSI `byTenantId`); Prüfung über `resolveApiClient` in `shared/api_client_auth.ts` (401 Token, 403 Scope / Client nicht `ACTIVE` / Mandant nicht `APPROVED`, ohne Cache). Fehlerformat `{ error, message }` und Routing nach `routeKey` gemeinsam über `shared/ext_http.ts` (`extError`, `dispatchExtRoute`). Clients legt nur das Betriebsteam an: `/onboarding/api-clients/{create,list,delete}` mit `x-admin-token`; `/onboarding/delete` räumt sie mit ab (Wipe ebenso, hat aber keine Route). Pro Version eigene Dateien mit fester Feldabbildung, der Kern in `shared/` kennt keine Pfade/Feldnamen. Einladungen `POST /ext/v1/invitations` (Scope `invitations.write`, läuft in der Lambda `invitations` mit eigener Routing-Tabelle `extRoutes`, Version in `invitations/ext_v1.ts`, Link über `buildInvitationUrl` mit `base_url` aus dem Draft bzw. `WEB_SURVEY_ORIGIN`, `signInvitations` gemeinsam mit der App-Route); die serverseitige Prüfung, wer Einladungen erzeugen darf, kennt damit neben `polly_deploy` auch diesen Scope. Umfragedetails `GET /ext/v1/surveys` und `/surveys/{surveyId}` (Scope `surveys.read`, Lambda `surveys_api`: `v1.ts` feste Feldabbildung ohne Platzhalter-Bedingungen, Antworten 60 s im Lambda-Speicher gecacht, Liste über `listProdSurveys` in `genesys_survey_check.ts`, Designs über `loadTenantThemesCached` in `shared/web_themes_table.ts`, Mandanten-Credentials über `attachTenantAuth`; `questionId` ist derselbe Schlüssel wie im Reporting). Reporting `GET /ext/v1/reporting/data` (Lambda `reporting_api`: `v1.ts` Parameter/Feldabbildung, `pagination.ts`, Routing-Tabelle im `handler.ts`; liest alle Sitzungen eines Zeitraums, sortiert und schneidet die Seite im Speicher; Tests in `test/customerApi.test.ts`). Dazu `GET /ext/v1/reporting/summary` (31 Tage, ohne Cursor, Zählung über `summarizeSlice` in `shared/session_summary.ts`, die auch die Vorschau im CSV-Export nutzt; bei Zeitüberschreitung 413). Dazu `GET /ext/v1/reporting/aggregates` (nur `surveyId`, `loadSurveyAggregates` in `shared/survey_results.ts` blättert über die `SurveyAggregatesTable`, `toV1Aggregates` in `reporting_api/v1.ts`; 404 bei laufender Löschung; Näherung über alle Versionen, siehe Kunden-Doku 5.3). Web-Designs `GET /ext/v1/web-themes` (Scope `themes.read`) und `POST /ext/v1/web-themes/import` (Scope `themes.write`, alles oder nichts, höchstens 50 Designs / 128 KB) in der Lambda `web_themes` (eigene Routing-Tabelle `extRoutes` vor `resolveTenantContext`, Version in `web_themes/ext_v1.ts`).
- **MCP-Schnittstelle** (in Arbeit, Plan mit Fortschritt: `documentation/implementationsplan_mcp.md`, Spezifikation: `documentation/polly_mcp.md`): KI-Clients (Claude Desktop, claude.ai, Claude Code) bearbeiten, deployen und werten Umfragen im Namen einer angemeldeten Person aus. Eigene Anmeldung (OAuth-Fassade mit Genesys-Login), getrennt von der Cognito-Anmeldung der Kunden-API; Rollen `polly_write`/`polly_deploy`/`polly_reporting` werden pro Tool-Aufruf serverseitig geprüft. Standardmäßig aus, nur mit Feature Flag `mcp`, `mcpEnabled` im Mandanteneintrag und `MCP_ENABLED` erreichbar. Stand: Spezifikation (M0), Spike (M1), Domain-Module Lambda-fähig (M2), Frontend-Vorarbeiten (M3), Backend-Bausteine (M4) in `amplify/functions/shared/`: `survey_pipeline.ts` (Validierungs-Pipeline, rein), `survey_store.ts` (Server-Spiegel von `surveyService.ts`, schreibt mit dem Genesys-Token der Person, Fehler als Codes), `genesys_datatable.ts` (`getRow`, `putRow`/`addRow` mit 429-Retry und Allow-List: nur `surveyDataTableId`, nur Zeilen `survey_<uuid>`/`survey_list`), `pseudonym.ts` (HMAC-Pseudonym, versiegelter Cursor), `reporting_limits.ts` (Grenzwerte gemeinsam mit der Kunden-API); Infrastruktur steht als Gerüst (M5): Tabelle `McpOAuthTable`, KMS-Key `McpTokenKey`, Secret `McpPseudonymSecret`, GSI `byMcpTenantKey` an `TenantsTable`, Lambdas `mcp`/`mcp_admin` (ohne Funktion: `MCP_ENABLED` ≠ `true` → 404 bzw. 501) mit Routen und Drosselung in `backend.ts`, Variablen `MCP_ENABLED`, `MCP_PUBLIC_BASE_URL`, `MCP_ALLOWED_REDIRECT_HOSTS`, `MCP_RESERVED_CONCURRENCY` (`shared/mcp_config.ts`).
- **Feature Flags** (`documentation/feature_flags.md`): `features` in der `__meta`-Zeile, nur beim Onboarding wählbar, danach nur direkt in der Data Table. Fehlend oder nicht `true` = aus. Registry aliasfrei in `domain/features/featureFlags.ts`, Abfrage über `app.hasFeature(key)` (für `web_survey` auch `app.webSurveyEnabled`). Nur Frontend, kein serverseitiger Schutz. Ohne `web_survey` sind Web-Designs, Web-Felder im Editor und Einladungslinks ausgeblendet; beim Speichern setzt `resetWebSettings` die Standardwerte. Die Einstellungsseite zeigt nur aktive Flags.
- **Setup/Uninstall** (`services/SetupOrchestrator.ts`, `SetupUninstall.ts`): legt Division (oder übernimmt eine bestehende, `createdBySetup: false`), Umfrage- und Mapping-Data-Table, OAuth-Client, Data Action an und merkt sich alles in `meta.setup` der `__meta`-Zeile – Uninstall ist davon abhängig.

## Spezifikation = `documentation/`

Die Markdown-Dateien in `documentation/` sind die fachliche Spezifikation (Constraints, JSON-Formate, API). Bei Änderungen an Editor-Format, Translator, Data-Table-Zeilen oder API **Doku und Code gemeinsam anpassen**. Die Test-Fixtures in `test/surveyFlowTranslator.test.ts` stammen aus den Beispielen in `survey_definition.md` / `survey_translator_for_flow.md`.

Nicht offensichtliche Regeln daraus (Auszug):
- `name` von Umfrage/Fragen wird automatisch aus Titel + erste 8 Zeichen der ID erzeugt und danach nie mehr geändert (Reporting-Schlüssel) – nicht editierbar machen, nicht neu generieren.
- Max. 20 Fragen inkl. aller Folgefragen.
- Flow-JSON für `rating`/`nps`: immer alle drei Bedingungen in fester Reihenfolge `equals`, `less_than`, `greater_than`; fehlende mit unerfüllbarem Wert (-1 / -1000 / 1000) und `next_question_id: null`.
- Fehlende Folgefrage ⇒ `null`, Flow fährt mit `default_next_question_id` fort (nicht Umfrage-Ende).
- Architect liest max. 32.000 Zeichen pro String. Das Flow-JSON wird gegen `FLOW_PAYLOAD_MAX_CHARS` geprüft (`domain/survey/flowPayload.ts`, re-exportiert von `services/flowPayloadBudget.ts`): Draft darf größer sein, Deploy wird gesperrt, Editor warnt ab 75 % (Messung entprellt in `useFlowPayloadSize`).
- TTS max. 3.000 Zeichen pro Anfrage: per TTS gesprochene Felder (Begrüßung, Verabschiedung, Fragetitel, Reprompt) werden im Validator hart begrenzt (`TTS_TEXT_MAX_CHARS`); Anzeige über `PromptTextarea` mit Prop `ttsLimit`. Neue gesprochene Felder dort ebenfalls markieren.

## Konventionen

- UI-Texte **immer** über vue-i18n (`src/i18n/locales/de.ts` ist das Schema, `en.ts`, `fr.ts`, `tlh.ts` und `la.ts` (Klingonisch, Testsprache, nur in der Dev-Ansicht wählbar und nie gespeichert) müssen dieselben Keys haben; neue Sprachen in `SUPPORTED_LOCALES` (`src/i18n/index.ts`) eintragen). Default/Fallback ist `de`. PrimeVue-Locales separat in `src/i18n/primevue/`.
- Code-Kommentare, Doku und Commit-Messages auf Deutsch.
- Frontend: `<script setup lang="ts">`, Alias `@/` → `src/`. Einrückung mit Tabs im Frontend, 2 Spaces in `amplify/`.
- Formatierung: maßgeblich sind `.editorconfig` und `.vscode/settings.json` (Tabs, 4 Spaces in `*.py`, 2 Spaces in `amplify/`, JSON/YAML/Markdown; LF, Zeilenumbruch am Dateiende). Es gibt keinen Formatter und `formatOnSave` ist aus: Bestehenden Code nicht umformatieren, Änderungen nur an den betroffenen Zeilen (keine reinen Whitespace-Diffs, einzeilige CSS-Regeln nicht aufklappen).
- Module/Sidebar werden in `src/app/modules.ts` registriert (`isActive` steuert Sichtbarkeit).
- Neue Lambda: `defineFunction` in `amplify/functions/<name>/resource.ts`, dann in `backend.ts` Tabelle granten, Env-Vars setzen, ggf. `attachTenantAuth(fn)` und Route an `httpApi` hängen. Ressourcennamen hängen an `envSuffix` (App-ID + Branch).

## Stolperfallen

- **Zwei Lock-Mechanismen**: `services/lockingService.ts` (App-weites Lock in `__lock`, TTL 15 min) und das Umfrage-Lock im Feld `lock` der `survey_<id>`-Zeile (Regeln in `domain/survey/surveyLock.ts`, Schreiben in `surveyService.ts`, Ablauf in `useSurveyLock.ts`, TTL `SURVEY_LOCK_TTL_MINUTES` = 60). Nicht verwechseln.
- **Genesys-Region** wird zur Laufzeit bestimmt: Frontend über `getGenesysRegion()` (`services/genesysRegion.ts`) aus `gcHostOrigin` der Start-URL (in `sessionStorage` über den Login-Redirect gemerkt), Backend aus Header `x-genesys-region` bzw. `genesysRegion` im Mandanteneintrag. Die Env-Variable `GENESYS_REGION` (Default `mypurecloud.de`, wirkt erst nach Build/Deploy) ist nur Fallback (Frontend: `define` in `vite.config.ts`, Backend: Lambda-Env → `DEFAULT_GENESYS_REGION`). Das Backend akzeptiert nur Regionen aus `amplify/functions/shared/genesys_regions.ts` (sonst könnte über den Header ein fremder Host als Genesys Tokens „bestätigen“); ein Test prüft die Liste gegen `PureCloudRegionHosts` des SDK. Keine Region-Strings direkt in den Code schreiben. Achtung: `services/genesys/region.ts` exportiert eine zweite, strengere `getGenesysRegion()` (wirft ohne `gcHostOrigin`, keine Prüfung gegen bekannte Regionen), die `appStore` beim Start verwendet.
- Data-Table-Zellen enthalten JSON als String. Spaltennamen sind case-sensitiv und kommen aus dem Schema im Setup (`Draft`/`Stage`/`Prod`/`Backup`/`lock`); auch `__meta` liegt im Feld `Draft`.
- DynamoDB-Tabellen haben `RemovalPolicy.RETAIN`: Umbenennen/Schlüsseländerung in `backend.ts` erzeugt neue Tabellen, alte bleiben liegen.
- Nicht committen/nicht bearbeiten: `dist/`, `amplify_outputs*.json`, `.amplify/` (generiert). `.env*` ist für Agents gesperrt.
- **Lambdas dürfen Module aus `src/` importieren** (esbuild bündelt ab Repo-Root, z. B. `domain/survey/flowNavigation.ts`), aber nur relativ und nur Module, die selbst keinen `@/`-Alias nutzen: `ampx` prüft vor dem Deploy mit `amplify/tsconfig.json` (kennt `@/` nicht, auch nicht bei `import type`), und `@/i18n` zöge vue-i18n ins Bundle (~1 MB). Gemeinsame Typen deshalb in `domain/survey/flowTypes.ts` bzw. `webSurveyTypes.ts`; ebenso gebündelt werden `domain/permissions/roleCheck.ts` und `constants/permissionConstants.ts`. - **API-Präfix**: Frontend, Setup und die URL der Data Action rufen das eigene Backend nie über fest verdrahtetes `/api` auf, sondern über `API_PREFIX` (`constants/apiConstants.ts`, Build-Variable `VITE_API_PREFIX`, Default `/api`). Hintergrund: Amplify-Rewrites gelten app-weit, ein zweiter Branch derselben App bekommt so ein eigenes Präfix und eine eigene Rewrite-Regel auf sein API Gateway. Der Dev-Proxy in `vite.config.ts` kennt nur `/api`. Einrichtung einer Branch-Umgebung: `documentation/branch_umgebung_einrichten.md`.
